# Баг: перевод средств не блокируется при недостатке средств — баланс счёта уходит в минус

## Описание
При создании перевода (`transfers`) с счёта с нулевым балансом система не проверяет достаточность средств. Баланс исходного счёта становится отрицательным и отображается в команде `/balance` как долг (overdraft).

## Ожидаемое поведение
Перевод должен блокироваться, если на исходном счёте недостаточно средств. Баланс не должен уходить в минус без явного overdraft-лимита.

## Фактическое поведение
1. Пользователь создаёт перевод со счёта с балансом 0 на другой счёт.
2. В таблицу `transfers` добавляется запись с `from_account_id = исходный счёт`.
3. При пересчёте баланса через `calculateAccountBalance` вычитается `outgoing` перевод.
4. Баланс исходного счёта становится отрицательным.
5. В `/balance` счёт отображается с минусом: `• Тинькофф: -1 000,00 ₴`.

## Где чинить
Валидация должна добавляться в месте **создания перевода** (веб-дашборд или другой источник записи в таблицу `transfers`). Бот только читает и отображает данные из БД, менять логику в боте не требуется.

## Приоритет
Средний — не блокирует основной сценарий, но приводит к некорректному отображению капитала в `/balance`.

**Дополнение:** то же происходит с обычными расходами (бот и дашборд не проверяют остаток), и защиты нет на уровне БД (нет триггера/CHECK). Исправление «только в вебе» не закроет бота — нужна проверка в общем слое или триггер в Postgres.

## 🔴 Высокий приоритет

### Баг 2: Лимит 1000 строк Supabase — баланс считается по неполным данным
**Описание:** `fetchTransactions`/`fetchTransfers` (бот) и `loadStore` (дашборд) грузят ВСЕ операции без пагинации. PostgREST отдаёт максимум 1000 строк, при `order desc` отрезаются самые старые. Баланс считается на клиенте (`calculateAccountBalance`).
**Ожидаемое:** баланс, Net Worth и `/balance` верны при любом числе операций.
**Фактическое:** после ~1000 операций балансы молча искажаются.
**Где чинить:** `apps/bot/src/db.ts:191-195`, `apps/web/src/services/data.ts:42-57`. Считать в БД (view `account_balances` уже есть, `supabase/schema.sql:143`) или пагинировать.
**Приоритет:** Высокий

### Баг 3: Бэкап из бота + восстановление в дашборде удаляет переводы и взносы
**Описание:** `/backup` не включает `transfers`, `goals`, `goal_contributions`, `users`, `category_groups`. `importStore` сначала удаляет transactions/transfers/goal_contributions, затем заливает только то, что есть в файле. Операция не атомарна.
**Ожидаемое:** восстановление возвращает полное состояние; сбой посередине не теряет данные.
**Фактическое:** после восстановления из бот-бэкапа все переводы и взносы в цели потеряны, балансы изменены.
**Где чинить:** `apps/bot/src/handlers.ts:331-338`, `apps/web/src/services/data.ts:416-462`.
**Приоритет:** Высокий

### Баг 4: Редактирование операции сдвигает время на часовой пояс
**Описание:** `new Date().toISOString().slice(0,16)` (UTC) кладётся в `datetime-local` (трактуется как локальное), при сохранении `new Date(occurredAt)` читается как локальное.
**Ожидаемое:** время операции не меняется при редактировании.
**Фактическое:** каждое сохранение двигает `occurred_at` на 2–3 ч; около полуночи операция уходит в другой киевский день и ломает «Сегодня» и Safe-to-spend. Нарушает правило `time.ts`.
**Где чинить:** `apps/web/src/components/TransactionModal.tsx:34,47,58`, `TransferModal.tsx:31`.
**Приоритет:** Высокий

### Баг 5: Правка корректировки (adjustment) переворачивает знак
**Описание:** при открытии на редактирование `setAmount(String(Math.abs(amount)))`, а для `adjustment` при сохранении знак не восстанавливается.
**Ожидаемое:** −500 остаётся −500.
**Фактическое:** −500 становится +500, баланс счёта смещается на 1000.
**Где чинить:** `TransactionModal.tsx:40,86`.
**Приоритет:** Высокий

### Баг 6: Перевод — сумма зачисления не пересчитывается при смене счетов
**Описание:** `amountTo` обновляется только при вводе `amountFrom`; смена селекторов счетов её не трогает. Нет проверки `amount_to == amount_from` для одной валюты.
**Ожидаемое:** сумма зачисления пересчитывается по курсу при любой смене счетов/суммы.
**Фактическое:** ввёл 4150 (UAH→UAH), сменил «куда» на USD-счёт → спишется 4150 ₴, зачислится 4150 $.
**Где чинить:** `TransferModal.tsx:38-50,88-112`.
**Приоритет:** Высокий

### Баг 7: Сумма в валюте, не совпадающей с валютой счёта
**Описание:** `calculateAccountBalance` не сверяет `tx.currency` с `account.currency`. Бот: `15$ такси` без активного USD-счёта → парсер берёт `accounts[0]`/любой UAH-счёт. Дашборд: селект валюты в модалке не связан со счётом жёстко.
**Ожидаемое:** валюта операции = валюте счёта, иначе ошибка/конвертация.
**Фактическое:** 15 «долларов» вычитаются из гривнового счёта как 15 ₴.
**Где чинить:** `packages/shared/src/calculations.ts:28-53`, `parser/regex.ts:116`, `TransactionModal.tsx:198-206`.
**Приоритет:** Высокий

### Баг 8: Кнопка «Сохранить» в боте сохраняет не тот черновик
**Описание:** один черновик на пользователя в `Map`. Два сообщения подряд — второй затирает первый. Кроме того, черновик удаляется ДО вставки в БД.
**Ожидаемое:** кнопка сохраняет именно то превью, под которым нажата; при ошибке БД можно повторить.
**Фактическое:** «Сохранить» под первым превью записывает второй черновик; при ошибке БД сообщение «Попробуй ещё раз» не помогает — черновика уже нет.
**Где чинить:** `apps/bot/src/input.ts:28,96,122` (ключ черновика — id превью-сообщения; удалять после успешной вставки).
**Приоритет:** Высокий

### Баг 10: Неверная дата следующего регулярного платежа
**Описание:** `new Date(y, m+1, day).toISOString().slice(0,10)`.
**Ожидаемое:** корректная дата следующего срабатывания.
**Фактическое:** (а) в UTC+2/+3 локальная полночь даёт предыдущий день (15-е → 14-е); (б) 31-е в коротком месяце перескакивает на следующий месяц; (в) первая дата всегда «следующий месяц», даже если день в этом месяце ещё не наступил; в дашборде дефолт `next_due` берётся по UTC.
**Где чинить:** `apps/bot/src/input.ts:314`, `apps/web/src/services/data.ts:236,402-404` — считать через `time.ts` с обрезкой дня по длине месяца.

**Фактическое:** пользователь видит 0 или неверный лимит без объяснений.

### Баг 13: `/cancel` и «❌ Отмена» не отменяют диалог `/recurring`

**Где чинить:** `apps/bot/src/handlers.ts:307-314`, `input.ts:33,211-216`.
**Приоритет:** Средний

### Баг 15: Парсер — ложные категории из-за поиска по подстроке
**Описание:** `lower.includes(synonym)`. Категория не сверяется с типом операции.

### Баг 16: Парсер — неверная сумма и тип дохода
**Описание:** берётся максимальное число из текста; ключевые слова дохода ищутся только между пробелами.

### Баг 32: Даты в экранах считаются мимо `time.ts` (UTC/локальный пояс браузера)
**Описание:** `Calendar` группирует по `occurred_at.slice(0,10)` и «сегодня» по `toISOString()` (UTC); `Recurring` определяет «к оплате» по UTC; `TransactionsView` и `IncomeView` — по локальному поясу браузера; симулятор бота — по UTC.

**Фактическое:** операция в 00:00–03:00 по Киеву показывается в календаре предыдущим днём; «к оплате» в этот интервал считается неверно; фильтры «Сегодня/Месяц» зависят от пояса компьютера.

### Баг 33: Календарь — корректировки показаны как расходы; «перерасход» считается от сегодняшнего лимита
**Описание:** в окне дня любая операция не-доход рисуется как «−сумма» (корректировка +500 → «−500»). Подсветка перерасхода сравнивает траты КАЖДОГО дня (и других месяцев) с `safePerDay` на сегодня, который сам уменьшается по мере трат.
**Ожидаемое:** корректный знак; подсветка по лимиту, действовавшему в тот день (или без неё для прошлых месяцев).
**Фактическое:** неверные знаки и «красные» дни, которые меняются от траты сегодня.

### Баг 34: Подтверждение регулярного платежа — дубли, потеря категории, неверный автор
